# 阶段1：窗口弹出原因与无打扰验证方案（只读审查）

审查日期：2026年10月29日。范围：现有验证入口、原生开图及命令桥、历史试出路径、本机ObjectARX 2020头文件、微软窗口隔离/事件接口文档。最初静态审查未调用CAD、COM或Win32窗口接口，也未修改共享C++或运行脚本。随后按根代理新授权，新增了独立隔离宿主工具并运行**无CAD机器自检**：分配/关闭私有desktop、启动/结束只读WinEvent监测、核实用户输入桌面和监测器线程桌面均未切换，未创建任何CAD进程。实现及边界见[隔离宿主使用与验收](原生接口探测/隔离桌面宿主使用与验收.md)。本报告不构成“AutoCAD/天正弹窗已修复”的运行结论，真实CAD结果由根代理另行取证。

用户最新约束：继续阶段1，先完成完整四侧轴网及连续编号；新增标注必须为相应天正专有对象。原方案只打开/保存过，建筑内容未改。现有冻结方案继续作为有哈希绑定的试验输入，原件不覆盖，暂不进入阶段2。

## 已有代码能确认的原因

| 证据 | 可确认的行为 | 不能由此直接确认 |
|---|---|---|
| `原生接口探测/运行全需求验证.ps1`的`$spec.Control`、`S1OPENPROBECONTROL`和`$cad.ActiveDocument.SendCommand`路径 | 每一Control批次都复制一个新control DWG，再向当前AutoCAD实例发送原生开图和业务命令。没有独立工作宿主，也没有不激活文档的合同 | 当前脚本没有`Visible=true`、`SetForegroundWindow`或`ShowWindow`，静态代码不足以确定每次Windows前台抢占的具体调用栈 |
| `NativeAccessProbe.cpp`的`nativeControlOpenApplicationCallback`（审查时约2079行） | `appContextOpenDocument(control)`打开文档，并强制验证新control已成为MDI活动文档。后续业务guard要求current、MDI活动文档和working DB都为control | “原生接口”不表示“无GUI活动”。现实现明确要求活动文档，但MDI活动与Windows前台窗口是两个层面 |
| `阶段1/运行原生接口探测.ps1:93` | 旧入口每250ms可能调用一次`$owned.Activate()`，直到目标文档处于活动状态 | 该旧脚本不是最近全需求runner的实现，不能把它每一轮都视为实际执行过 |
| `阶段1/试出PDF.ps1:10`、`原生接口探测/试出方案验证.ps1:19`、`试出测点改动.ps1:13` | 历史预览会显式Activate，或在可见实例中Documents.Open；会改变活动图 | 不能把这些历史预览的窗口行为自动归给最新原生AcPl输出 |
| `NativePlotProbe.inc`的`NativePlotBackgroundScope::activate()` | 这个`activate()`只临时设置并核对BACKGROUNDPLOT=0，随后恢复，不是窗口Activate。最新原生打印避免另起后台打印任务的处理已存在 | 老的BACKGROUND_PLOT=2试验曾产生后台打印工作进程；不应把新打印代码的函数名误判为抢前台原因 |

当前代码库排除归档和run后，未定位到启动新acad.exe或显式设置AutoCAD Visible=true的脚本。现阶段更准确的解释是：在用户同一个可见CAD宿主中，反复创建并切换活动图；旧预览还显式激活文档。天正浮动面板究竟由哪个命令、文档激活回调或模块加载触发，现有回执没有记录窗口类名/SHOW事件，仍须现场观察。不能将所有天正弹窗都归给TMultAxisDim，因为最新已成功的TDelLabel/TReAxisNo路径并未调用该命令。

## 本机SDK能提供的机制与边界

来源：`C:/Autodesk/ObjectARX_for_AutoCAD_2020_Win_64_bit/inc/acdocman.h`。

- `setCurDocument(doc, mode, activate=false)`允许在ApplicationContext内临时切换数据操作上下文而不激活文档（约298–311行）。它不等于可以让所有天正编辑器命令在非活动图中运行。
- `sendStringToExecute(doc, text, bActivate=true, bWrapUpInactiveDoc=false, bEchoString=true)`有关闭激活的参数（约316–325行）。`false,true,false`可作为有范围的试验候选，但现有天正点拾取、ZOOM及严格guard依赖MDI活动图，不能直接放宽guard去用户后台文档尝试，否则天正内部若使用MDI活动图会有对象归属风险。
- `appContextOpenDocument(DocOpenParams*)`在2020 SDK中可用。`kUseUI=0x40`表示允许弹出/确认消息，`kUseUIOnErrors=0x10`表示错误UI（约346–385行）；新非交互开图路径应显式不置这两个位，并提供完整路径、初始视图和错误记录。它只约束该开图调用，不保证天正命令或主窗口不自行显示。
- `disableDocumentActivation()`限制用户切换文档，必须恢复（约400–410行）。这不是防止窗口抢前台的方法，不应在用户当前CAD上长期锁定文档切换。
- `beginExecuteInCommandContext`的2020头文件说明：回调在MDI活动文档执行，并会取消已有未完命令（约415–435行）。不能将其当通用“无打扰队列”直接用于用户CAD。
- `acedCommandS`只适合完整输入的命令。`acedCmdS`的额外`AcApDocument*`参数在`acedCmdNF.h:34–54`明确保留作未来用途；不能把它当2020版指定任意后台文档的接口。

本地天正帮助把部分命令定义为先面板后点选。不能仅设置FILEDIA=0就声称所有天正面板已消失。四侧试验应优先复用已取得完整点式协议的TDelLabel/TReAxisNo，避免再次走未明确后台参数的TMultAxisDim等入口。

## 建议的非打扰实施顺序

1. **先建立可证据化的窗口基线。** 在任何CAD操作前记录用户输入桌面、前台HWND/PID以及已有AutoCAD进程，安装只读事件监测。不要为了制造“没弹窗”结果主动切换用户前台窗口。
2. **避免继续往用户可见CAD里逐批开control。** 将四侧创建、位置调整、连续编号、保存/新库回读及必要PDF汇为一个任务批次。一个批次只绑定一个方案副本、一个宿主PID、一个C++候选及资源合同，避免每个小步骤都Open/Activate/Load/Unload。
3. **优先使用本任务专用宿主。** 业务对象仍全由ObjectARX C++和公开天正命令处理；控制器只负责该宿主的启动/调度与回执。不要对用户现有AutoCAD设置Visible=false、最小化、关闭或强制恢复前台。新的宿主必须按进程ID/启动参数/窗口归属绑定，不能依赖全局GetActiveObject恰好返回想要的实例。
4. **先小样本实测普通隐藏宿主。** 一次隐藏启动＋稳定IPC/native bootstrap，完整命令输入，不调出预览DWG。若天正仍自行SHOW，则不把“随后又隐藏了”判定为通过，也不无限循环Hide/Restore。
5. **同桌面隐藏不足时，隔离到任务私有Windows桌面。** Win32的CreateDesktopW和STARTUPINFO.lpDesktop可把新工作进程窗口放到另一桌面；不调用SwitchDesktop，不改变用户输入桌面。微软提供该通用机制，但AutoCAD/TArch的许可初始化、图形选择缓存、原生命令和PDF设备能否在该桌面实际工作，仍需本机先证，再进行四侧试验。此方案不是把ARX改成CRX，也不是假定Core Console能加载所有天正GUI模块。
6. **遇意外对话框要明示失败。** 记录所属PID、窗口类、标题和阶段；停止发更多命令，保存日志。只处理本任务专用宿主，不取消用户CAD命令、不终止用户进程、不放宽源图/工作副本身份检查。

普通隐藏启动不能独自给出保证：微软文档说明STARTUPINFO的wShowWindow主要约束GUI第一次ShowWindow，后续显式ShowWindow可以覆盖。见[STARTUPINFOW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-startupinfow)。因此`Start-Process -WindowStyle Hidden`只能是启动配置，不能替代整个执行期的事件验证。

私有桌面是候选隔离机制，非本机已验证结果。其创建和指定进程桌面的接口分别见[CreateDesktopW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-createdesktopw)和[STARTUPINFOW.lpDesktop](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-startupinfow)。桌面/进程句柄须按所有权关闭；不要更改系统桌面heap或全局焦点策略来完成一次阶段1验证。

## “窗口问题已解决”的验收要求

| 记录 | 必需内容 | 通过口径 |
|---|---|---|
| 监测完整性 | 从启动前到完成/清理后的持续记录；事件hook启动/结束、错误、丢失及样本次数 | 不能仅两个before/after快照；监测失效为Unknown |
| 用户桌面前台事件 | 每个EVENT_SYSTEM_FOREGROUND的时间、HWND、PID/进程归属，关联阶段 | 自动化宿主/天正窗口未成为用户输入桌面前台；用户自身操作另记，不假称可归因 |
| 用户桌面窗口事件 | CREATE/SHOW/HIDE/DESTROY，根/所有者、类名、可见性、进程族与桌面归属 | 执行期间没有工作宿主/面板在用户桌面显示；“显示后快速Hide”不算无弹窗 |
| 工作宿主状态 | 稳定唯一PID、TCH已加载、当前control及working DB、命令trace、heartbeat/完成marker | 不能以worker没弹但卡在隐藏对话框当成功；对应业务原生结果还须通过 |
| 私有桌面方案 | 用户输入桌面前后及持续归属、worker线程桌面/窗口归属；无SwitchDesktop | 用户桌面未切换；worker自己的不可见桌面可有正常GUI窗口，不把IsWindowVisible=true误当用户可见 |
| 输入和清理 | 原文件/冻结快照哈希；只关闭本任务宿主、native回调安全释放、唯一ARX/INI清理 | 无用户CAD关闭/用户前台强制还原；源文件保留 |

可使用只读OUTOFCONTEXT WinEvent监测，不要向AutoCAD注入hook DLL。微软[SetWinEventHook](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwineventhook)要求安装线程有消息循环；托管回调要保持强引用/GCHandle；idProcess=0覆盖的是调用者当前桌面。监测器若在用户桌面，应验证用户侧零显示/零抢前台；工作桌面还要有单独的进度/窗口状态记录，不能假定一个hook跨所有桌面。

## 对当前阶段1结论的影响

此前原生几何/业务命令限定通过仍是有效证据，但不包含“验证完全不打扰用户”。在窗口事件和业务结果同时通过之前，不能说窗口问题已解决。用户已确认新标注必须为天正类型，不能为了躲避天正面板改画普通AutoCAD文字、尺寸或圆圈并计通过。完整四侧及连续编号仍由专用方案副本和天正真实对象承担，阶段2尚未开始。
